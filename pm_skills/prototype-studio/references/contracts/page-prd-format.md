# 页面 PRD 版式规范

页面 PRD 面向产品、设计、业务和评审人员。正文使用页面名称、页面区域和用户看得懂的业务表达，不展示页面 ID、研发字段名、对象路径或决定编号。`pages.json`、`data.json` 和 `decisions.json` 继续作为内部校验依据，不复制到阅读版 PRD。

## 固定结构

每份页面 PRD 使用四个一级内容区：

1. **页面说明**：用一段话说明面向谁、解决什么问题、通常从哪个页面进入，以及能完成哪些主要事情。
2. **页面字段逻辑**：这是正文主体。按页面从上到下、从左到右的顺序，为每个用户可见的业务字段建立一张独立表格。
3. **页面整体逻辑**：记录无法只归入一个字段的跨字段、跨状态、跨页面或长任务逻辑；每项逻辑单独成表。
4. **页面状态机**：按已确认的业务规则说明页面有哪些状态，以及用户操作、数据变化或系统结果怎样推动状态变化。

不单独设置页面跳转、标准件与视觉约束、AI与性能、验收或待确认章节。跳转写在相关操作的结果中；AI、性能和未确认规则用完整语句写进对应字段、整体逻辑或状态机。标准件和验收细节仍由项目设计规范、内部合同与验收记录维护。

## 字段表格

这里的“字段”指页面上的业务信息或输入项，例如课程名称、截止时间、状态、提交进度和学生列表，不是数据库字段。每张字段表固定包含：

| 说明项 | 写作要求 |
|---|---|
| 字段类型 | 写页面呈现或交互类型，不写 string、number 等数据类型。可使用 Label、Status Tag、Input、Textarea、Combobox、Select、Radio Group、Checkbox、Switch、Date Picker、Date Time Picker、Upload、Button、Link、List、Table、Card、Progress Bar、Chart、Avatar/Image、Rich Text，必要时组合使用。 |
| 页面上显示的文字 | 写用户实际看到的标签、内容格式、空状态和错误提示。示例数字或名称标明是演示内容。 |
| 字段位置 | 使用“页面顶部基本信息区域、作业名称下方”等页面区域和相对位置，不使用组件名、CSS选择器或代码路径。 |
| 数据来源逻辑 | 优先写成“来自哪个页面的哪个位置，由谁通过什么操作产生”。计算结果用文字说明输入、筛选条件、去重方式和计算规则。外部系统或后台配置写清来源和维护方。 |
| 展示逻辑 | 说明什么时候显示、显示成什么格式、没有数据或发生异常时显示什么，以及不同角色看到的差异。 |
| 操作逻辑 | 说明谁能操作、什么条件下可以操作、成功/失败/取消后发生什么，以及哪些页面同步变化。只读内容说明不能操作及原因。 |

来源或规则不明确时，直接写出需要用户回答的完整问题，例如“已退出课程的学生是否继续计入应提交人数，目前没有明确规则，需要用户说明”。不要只写“待确认”，也不要用 `Q-013` 等内部编号代替问题。

独立按钮如果不承载业务数据，放入页面整体逻辑；按钮文字、位置或显隐本身需要单独说明时，可以按字段表登记，数据来源逻辑写它受哪个页面状态或权限控制。

## 页面整体逻辑表格

页面打开、状态判断、保存发布、跨页同步、批量操作、AI生成和异常恢复等逻辑逐项写，不合并成长段落。每项固定包含：

| 说明项 | 写作要求 |
|---|---|
| 触发时机 | 写清用户动作、页面事件或业务状态。 |
| 涉及内容 | 使用页面上的业务名称列出受影响字段和操作。 |
| 处理逻辑 | 用日常语言说明处理顺序、判断条件和计算方法，不写接口名或程序方法。 |
| 页面结果 | 写清当前页面最终显示什么、允许继续做什么。 |
| 对其他页面的影响 | 使用页面名称说明同步结果；没有影响时明确写“无”。 |

## 页面状态机

状态机只记录会改变页面整体内容、主要操作方式或业务阶段的状态。字段自身的显示、隐藏、禁用和格式变化继续写在该字段的“展示逻辑”中。鼠标悬停、输入框聚焦等纯视觉变化不用进入状态机，除非它们会改变业务结果。

先用“状态说明”表列出已确认规则中的状态。新页面可以先写状态机再实现；已经确认但尚未实现的状态，在对应说明中写明“已确认，待实现”。既有实现与已确认规则不一致时记录差异，不能把漏做的分支从 PRD 中删掉，也不能直接把代码行为当作需求。

| 状态名称 | 进入条件 | 页面表现 | 可进行的操作 | 离开条件 |
|---|---|---|---|---|
| 使用用户能理解的业务名称 | 说明页面为什么进入该状态，包括首次打开或重新进入时的选择条件 | 说明用户此时看到什么 | 说明谁可以进行哪些主要操作 | 说明什么情况会结束该状态；流程终态可写“流程到此结束”，稳定只读状态可写“本页无后续变更” |

再用“状态变更”表逐条说明状态之间怎样变化：

| 当前状态 | 触发动作或事件 | 判断条件 | 变更后状态 | 页面变化 | 对其他页面的影响 |
|---|---|---|---|---|---|
| 当前业务状态 | 谁做了什么，或发生什么页面事件、系统结果 | 所需权限和业务条件；没有时写“无” | 进入的业务状态；状态不变也要明确写出 | 当前页面内容和操作的变化 | 使用页面名称说明同步结果；没有时写“无” |

状态变更覆盖已确认规则中适用的成功、失败、取消和数据为空等分支，包括操作后仍处于原状态的情况。首次打开、刷新或重新进入时，说明如何根据当前数据选定或恢复状态；不强迫所有页面经过同一个初态。合法终态不必虚构返回或重试操作；确实只有一个稳定状态时，保留本节并说明没有状态变更，不为填表编造动作。

业务阶段、弹窗开关等状态若能同时存在，按不同流程分别列两张表，不枚举它们的所有组合。页面整体逻辑写处理步骤，状态机写流转条件和结果；重复的复杂处理用“按本页‘保存作业’逻辑处理”等业务名称引用。字段中涉及业务阶段变化时，要与状态机一致。

状态名称不写技术枚举、页面 ID 或内部编号。规则没有确定时，直接写出需要用户回答的完整问题；不能仅凭已有界面自行批准新状态。

## 写作边界

- 页面 PRD 写业务和交互规则，研发自行定义数据库结构、接口和代码字段。
- 来源优先使用页面名称和页面位置；确实没有页面来源时如实写外部系统、后台配置、人工导入、计算结果或AI生成。
- 不从已经画出的界面反推未经确认的业务事实。新出现且找不到来源的内容先提出完整问题，独立内容可以继续整理。
- 不在多个页面 PRD 中复制同一份数据定义。每页说明当前页面怎样取得、展示和操作该内容，内部合同负责跨页一致性检查。
- 使用简短、直接、日常的中文。能说“教师保存后，学生端同步更新”，就不写“触发数据持久化与消费端刷新”。
